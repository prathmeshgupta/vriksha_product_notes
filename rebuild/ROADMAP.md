## R0 — Project scaffold

**Status**: a default `npm create vite@latest -- --template react-ts` scaffold exists at this point, unmodified, not yet installed or customized. Nothing else has been built.

**Scope**: install dependencies, verify the default scaffold runs (`npm run dev`), add TypeScript strict mode, add a linter/formatter (the scaffold includes `oxlint` by default — decide whether to keep it or switch to ESLint+Prettier), set up the folder structure defined in `ARCHITECTURE.md`, configure Vite for GitHub Pages deployment (base path, build output location), add the Supabase client library and environment variable handling for the publishable key.

**Explicitly not in scope for R0**: any actual product UI, any Supabase queries, any design tokens beyond placeholder values.

**Deployment mechanism — resolved 2026-07-16** (previously an open Blocking item in an earlier draft of this doc): GitHub Pages only serves whatever branch is set in Settings → Pages, and switching it is a fast, reversible dropdown change — not a rebuild, not a git operation, no risk to `main`. Preview during R0-R7 is local-only (`npm run dev`); the rebuild only ever pushes to the `rebuild` branch; Pages configuration stays on `main` untouched until R8 cutover is explicitly approved. See `ARCHITECTURE.md` §1.

**Decisions — resolved 2026-07-16**:
1. **Linter: ESLint (flat config) + `typescript-eslint`**, not the scaffold's default `oxlint`. Reason was not preference but a hard compatibility issue: `oxlint` and Vite 8's default toolchain both ship native Rust binaries (`@oxlint/binding-*`, `@rolldown/binding-*`, `lightningcss-*`), and in the sandbox environment used to build this scaffold, running either crashed immediately with a SIGBUS ("Bus error (core dumped)", exit 135) — confirmed reproducible even via `--version`, and confirmed not an architecture mismatch (host is x86_64, binaries were x86_64). Vite itself was pinned back to `^5.4.11` (the last pre-Rust-rewrite line) paired with `@vitejs/plugin-react@^4.3.4` to route around the same class of crash, and `oxlint` was dropped for the same reason rather than leaving one native-binary risk in place after removing the other. ESLint is pure JS, has no native-binary crash risk, and is the more mature/battle-tested option regardless.
2. **Test framework: Vitest**, confirmed (Vite-native, no separate config needed, works with the pinned Vite 5.4 line).

**Definition of Done for R0**: scaffold installs and runs locally (`npm run dev`) ✅, TypeScript strict mode on with zero errors ✅, both tooling decisions above confirmed and recorded ✅, folder structure from `ARCHITECTURE.md` §3 — pending, folder structure from `ARCHITECTURE.md` §3 exists (even if mostly empty), Supabase client connects successfully to the real project (a trivial "fetch and log one row" smoke test, not real data-layer code — that's R2).

**Known sandbox-environment gotcha, documented for any future session continuing this build**: this development sandbox has at least two independent flakiness sources unrelated to the code itself, both worked around during R0 and worth knowing about before assuming a similar failure is a real bug: (a) a class of newer Rust-native Node addons (Vite 8's `@rolldown`/`@oxc-project` binaries, `oxlint`, `lightningcss`) reliably SIGBUS-crash in this specific sandbox even though the binaries are architecture-correct — avoided by pinning Vite to the `5.4.x` line and using ESLint instead of oxlint; (b) file writes to the sandbox's `outputs` mount have intermittently landed truncated or null-byte-padded even when the write tool reported success (seen on `tsconfig.app.json`, `tsconfig.node.json`, `package.json` during R0) — always verify a freshly-written config file's exact byte content (e.g. `python3 -c "open(f,'rb').read()"`) before trusting a parser's error message about it, since a "syntax error" a few bytes from EOF is more likely mount corruption than an actual mistake in what was written.

**Incident, 2026-07-16 — frozen app's `index.html` overwritten by the R0 scaffold copy, found and fixed same day (see `R0_INDEX_HTML_FIX.md` in this folder for the full account)**: the scaffold's default Vite entry file and the frozen app's single-file app both happened to be named `index.html`. Moving the scaffold into the repo root via `robocopy ... /E` silently overwrote the real ~200KB frozen app with Vite's 370-byte stub, and this got committed and pushed to `rebuild` before it was noticed (during the start of R1, when grepping the "frozen" `index.html` for exact CSS values returned nothing). No data was lost — `main` was never touched, `stable`/`pre-phase1-stable` were unaffected, and all product data lives in Supabase, not this file — but it was a real, avoidable mistake in the R0 instructions. Root cause and fix: renamed the rebuild's Vite entry point to `app.html` (`vite.config.ts` now sets `build.rollupOptions.input: 'app.html'` and `server.open: '/app.html'`) specifically so the two apps can never again share a filename at the repo root.

**Guardrail added as a result — apply this to every future phase, not just R0**: before any bulk file copy between the sandbox/scaffold and the repo root (`robocopy`, `cp -r`, `xcopy`, or equivalent), first diff the *filenames* of what's being copied against what already exists at the destination (e.g. `Compare-Object (dir source -Name) (dir dest -Name)` in PowerShell, or just `dir` both and eyeball it for anything besides genuinely new files/folders). If any filename collides with something that isn't supposed to be touched, stop and rename or exclude it before copying — don't rely on memory or assumption that "the scaffold only has new files." This applies most obviously to `index.html` (now resolved by the rename) but the same check should happen again at R8 cutover time, when `rebuild`'s contents may eventually need to merge into `main` for real — that merge needs the same collision check, deliberately, not via a blind bulk copy.

**Third sandbox gotcha, found during R2 (2026-07-16/17): a from-scratch `npm install` cannot reliably complete in this sandbox.** Every sandbox shell call is hard-capped at 45 seconds and appears to run in its own torn-down process namespace, so a full dependency install (~200+ packages, no warm cache) that runs past that window doesn't pause and resume on the next call — it gets killed mid-write. This showed up as `ESLint` hanging indefinitely (`timeout 124`) on every file, including ones that had linted cleanly minutes earlier; the actual cause, confirmed by importing each dependency individually, was that `@typescript-eslint/eslint-plugin` and `@typescript-eslint/scope-manager` were silently absent from `node_modules` despite `npm ls`/the install log both reporting success (npm's own cleanup step had thrown `EPERM` on stale `esbuild` platform binaries mid-install and left the tree partially populated). A second from-scratch install attempt in a clean directory reproduced the same kill-mid-install pattern, once even leaving `node_modules/ajv` mid-rename (`ENOTEMPTY` on the next attempt). None of this reflects on the actual source files — `tsc -b --force` passed cleanly throughout, on the exact same file set, in the same sandbox. **Takeaway for future sessions**: if `npm install` in this sandbox needs to pull most/all packages fresh (no populated `node_modules` to reuse), do not trust the sandbox's own `eslint`/`vitest`/build output as authoritative — verify TypeScript correctness via `tsc -b --force` (fast, reliably completes) and a manual review against the exact rules in `eslint.config.js`, then treat the user's local machine as the source of truth for `npm run lint`/`npm run build`, since it has a real, already-populated `node_modules` and isn't subject to this per-call timeout.

## R1 — Design tokens + component library

**Goal**: encode the Vriksha design palette (forest greens, gold accent, Lora/JetBrains Mono typography, existing card/button/status-pill/callout visual language) as reusable, typed React components, before building any real screens on top of them.

**Why first**: per `STRATEGY.md`, the design system's reuse value is the main reason a framework was chosen over vanilla JS. Building it first means every subsequent screen composes it rather than a screen being built ad-hoc and the design system retrofitted after.

**Scope**: CSS custom properties / design tokens file matching the frozen app's `:root` variables exactly (colors, radius, etc.) — see `ARCHITECTURE.md` §2 for the exact token values pulled from the live app. Core components: `Button` (with primary/danger/small variants), `Card`, `StatusPill` (published/draft/compliant/non-compliant variants), `Callout` (with warn/danger variants), `Pill`, form field primitives (text input, number input with min/max, select, textarea) matching the frozen app's `.field-row`/`.field-label` pattern. A small Storybook-style demo page (or just a `/dev/components` route) to visually verify each component against the frozen app's live screenshots before moving on.

**Verification before moving to R2**: side-by-side visual comparison against the frozen app for every component built — not just "does it compile," but "does it look identical."

## R2 — Data layer

**Goal**: typed, tested access to the same Supabase project the frozen app uses — no new tables yet, just correctly reading/writing the existing schema.

**Scope**: Supabase client setup (same project, same publishable key pattern as the frozen app). TypeScript interfaces for every table currently in the schema: `products`, `product_versions`, `templates`, `portfolio_holdings`, `portfolio_holdings_history` — field-for-field matching what's documented in the frozen app's `ARCHITECTURE.md` §2. Auth flow (login screen, session handling) re-implemented — this is the second place (after the original `supabase`/`sb` naming collision bug) where a subtle bug could silently break the whole app, so extra care and explicit testing here. A typed data-access layer (functions like `getProduct(id)`, `listProducts()`, `publishProduct(id, note)`) that the UI calls, rather than raw Supabase calls scattered through components — this is one of the concrete structural improvements TypeScript+modules is supposed to deliver over the frozen app's approach.

**Verification before moving to R3**: can log in, can read the real 9+ products from the real database, types compile with no `any` escape hatches on the core data shapes. This is flagged elsewhere in this doc as a place a subtle bug could silently break the whole app (same class of risk as the frozen app's original `supabase`/`sb` naming collision) — so verification explicitly includes session-expiry and token-refresh behavior (log in, wait past a token's normal lifetime or force-expire it, confirm the app degrades to a clear re-login prompt rather than silently failing every subsequent request) and logout, not just "can log in once."

## R3 — Product note viewing, editing, versioning/publish

**Goal**: re-implement the core workflow — view a product note, edit every field type the frozen app supports (freeform text, numeric cap ranges, sleeve/variant/allocation arrays), publish a version, view history/diff.

**Scope**: this is the single biggest re-implementation phase, since it's most of what the frozen app's `index.html` actually does. Needs care in re-reading exactly how the frozen app's editor handles each of the 4 product "shapes" (single-sleeve, strategic-allocation, risk-variant, goal-based) — see the frozen app's `PROJECT_HISTORY.md` §2 (structured caps rework) for the exact field semantics (`sleeveMinPct`/`sleeveMaxPct`/`positionMinPct`/`positionMaxPct`/`positionBasis`/`sectorCapMaxPct`) before building the corresponding editor components.

**Scope also includes archive/unarchive** — not a separate phase, folded into R3 since it operates on the same product record and status field as the rest of this phase's work.

**Verification before moving to R4**: can edit and publish a real product note in the new app and see the resulting `product_versions` row match what the frozen app would have produced for the same edit; can archive and unarchive a product and see it correctly move between the active/archived views.

**Status**: ✅ Done (commit `1ae7cda` on `rebuild`, 2026-07-20; build and lint verified clean locally, 0 errors). Sidebar nav (grouped by category, search, archived link, collapse toggle), overview grid, read-only note view (all 4 archetypes), full editor (Key Facts, Objective/Philosophy, Construction Rules + caps, style sleeves / strategic allocation / risk variants / goal framework depending on archetype, key risks), publish flow (note prompt, no compliance gate yet -- that's R6), version history + word-level diff, archive/unarchive. Export/Email buttons intentionally omitted (R4), Compliance button intentionally omitted (R6) -- not stubbed, per `STRATEGY.md`'s "no half-built UI" preference.

**R2's `data/types.ts` had 3 real gaps, found and fixed while building R3's editor against it** (a good example of why "verify against the frozen app's actual behavior, not the sampled data" matters -- R2's types were derived from `information_schema`/sample-row inspection, which missed fields that were simply null/absent in every sampled row):
1. `CapRange` only had `sleeveMinPct`/`sleeveMaxPct` -- missing `positionMinPct`/`positionMaxPct`/`positionBasis`, which the frozen app's `capFieldsHtml()` proves are real, live-edited fields on every sleeve/allocation row, not just the top-level construction rules.
2. `PortfolioConstructionRules` was missing `sleeveMinPct`/`sleeveMaxPct`/`positionMinPct` entirely (had `positionMaxPct` only).
3. `ProductNoteCommon` was missing `selectionMethodology`/`portfolioConstruction` (freeform prose fields checked generically in the frozen app's editor/read view/`DIFF_FIELDS`, not scoped to one archetype); `RiskVariant` was missing `factorMix`/`universe`/`stockCount`/`referenceIndex`/`rationale` (a second optional field set for systematic/factor-based variants).

**A real TypeScript pitfall hit and fixed while wiring the editor**: `Partial<ProductNoteData>` does not mean "any subset of fields from any archetype" -- `keyof` on a union type only includes fields common to *every* member, so a naive `patch(fields: Partial<ProductNoteData>)` helper would have rejected `{ styleSleeves }`, `{ variants }`, etc. outright as a compile error. Fixed in `ProductEditor.tsx` with an explicit intersection of each archetype's own `Partial<...>`, which correctly gives the union of all fields, each optional. Worth remembering for R4/R5/R6 if similar "patch the note generically" helpers come up again.

**Sandbox note**: directory operations (even a plain `du -sh` on `node_modules`) started timing out against this sandbox's 45-second-per-call limit partway through R3, on top of the from-scratch-`npm install` limitation already documented above. Verification for R3 fell back to `tsc`-free manual line-by-line review against the exact types/imports (same fallback as R2's ESLint gotcha) rather than a sandbox-side compiler run. Your local `npm run dev`/build/lint below is the first real compiler pass this code gets.

## R4 — Exports and CSV upload

**Goal**: re-implement Word/Excel/PDF export and CSV constituent upload.

**Scope**: same underlying libraries the frozen app uses (docx.js, SheetJS/xlsx, jsPDF+autotable, PapaParse) — no reason to switch libraries, just re-implement the document-generation logic in a typed, modular way instead of one long function per format. Reuse the frozen app's `formatCapsSentence()`-equivalent single-source-of-truth pattern so the note display and every export format read from the same formatting function, not duplicated logic.

**Verification before moving to R5**: exported documents for the same product, same version, are content-equivalent to what the frozen app produces (not necessarily byte-identical, but same information, same structure).

**Status**: implementation complete, not yet committed. Built: `lib/exportExcel.ts` (`exportProductXlsx`, `exportAllProductsXlsx`), `lib/exportWord.ts` (`exportProductDocx`), `lib/exportPdf.ts` (`exportProductPdf`, `exportClientSummaryPdf`), `lib/email.ts` (`productToPlainText`/`buildMailtoUrl`/`emailNote`), `features/products/CsvUploadView.tsx`, `data/holdings.ts`'s new `replaceHoldings()`. Wired into `ProductDetail.tsx`'s toolbar (Word/Excel/PDF Full/PDF Client Summary/Email, in the frozen app's exact order), `ProductOverview.tsx` ("Export All → Excel"), and `AppShell.tsx` (new "CSV Constituent Upload" nav item, same pattern as R3.5's Backup & Sync/Upgrade Roadmap).

Ported faithfully from the frozen app's `exportXlsx`/`exportAllXlsx`/`productToRows`/`exportDocx`/`exportPdf`/`exportClientSummaryPdf`/`PDF_THEME`+helpers/`productToPlainText`/`buildMailtoUrl`/`emailNote`/`renderCsvView`/`handleCsvFile` (repo root `index.html`), re-reading the actual source line-by-line before porting rather than working from memory, same rigor as R1-R3. Field names adapted the same way the R3 read-only view already was: free-text `weightRange`/`range`/`stockCountRange`/`cashBuffer` replaced with `formatMinMaxRange()`/`formatCapsSentence()` over the structured numeric fields.

**Two disclosed deliberate deviations, per `STRATEGY.md`'s "disclose, don't silently redesign" rule**:
1. **CSV upload now persists to real `portfolio_holdings` via a new `replaceHoldings()` bulk function**, instead of the frozen app's ephemeral, never-persisted `uploadedConstituents[pid]` in-memory map. Justified because the rebuild already has a real holdings table and typed CRUD (R2), and R6's Compliance Engine needs real holdings data to check against -- building it ephemeral here would just be throwaway state needing replacement later. The Save is a separate, explicit, confirm-gated step from parse/preview (full delete-then-insert replace of that product's holdings, not a merge), since it's now a real destructive database write rather than a same-tab-only in-memory assignment.
2. **`exportAllProductsXlsx`'s filename uses the live product count** (`Vriksha_Product_Notes_All${n}.xlsx`) instead of the frozen app's hardcoded `_All9` -- hardcoding "9" would silently go stale the moment R5's create-product flow adds a 10th product.

**Structural difference from the frozen app, not a design change**: the frozen app read `entry.versions`/`uploadedConstituents` synchronously from in-memory state inside every export function. The rebuild fetches `product_versions`/`portfolio_holdings` from Supabase, so every export function here is `async` and the caller `await`s it -- surfaced in the UI as a disabled-while-exporting button state plus a `Callout` error banner on failure, replacing the frozen app's `alert()` (matching the error-banner pattern R3.5's `BackupView` already established).

**Typing note worth remembering for future PDF-related work**: `jspdf-autotable`'s side-effect import (`import 'jspdf-autotable'`) augments the `jsPDF` class so `doc.autoTable(options)` is fully typed with no cast. Reading the result back (`doc.lastAutoTable.finalY`) goes through a narrow `unknown`-cast helper (`readFinalY()` in `exportPdf.ts`) instead of `any`, because the package's bundled declaration for `lastAutoTable` is broader (covers call patterns this file doesn't use) than the shape it actually produces after a plain `autoTable()` call.

**No sandbox compiler run** (same limitation documented in R0/R2/R3): this was reviewed manually, file-by-file, against the exact types in `data/types.ts` and the exact library APIs (`xlsx`, `docx`, `jspdf`+`jspdf-autotable`, `papaparse`, `file-saver`) rather than via a real `tsc`/ESLint pass. R4 is also the **first phase with new npm dependencies** since R0's scaffold -- `npm install` is a required step before your local `npm run dev`/`build`/`lint` will succeed (see the verification steps given alongside this update). Manual review is a documented insufficient substitute for a real compiler pass (R3's Round 2 found 27 real `tsc` errors manual review missed) -- treat your local build as the actual verification, not this review.

**Follow-up fix, same day: `replaceHoldings()` made transactional.** Discussed with the user right after the above landed -- the delete-then-insert in `replaceHoldings()` was two separate client calls with no transaction tying them together, so a failed insert (bad row data, a dropped connection) after a successful delete left the product at zero holdings instead of its prior ones. Decided to split the fix from the separate, larger "add a real audit trail for holdings changes" discussion (see R6 below) rather than bundle both: the transactional gap is a plain correctness bug live the moment CSV upload ships, the audit trail is about forensics after a user-initiated bad upload (lower severity, already partly covered by the CSV screen's confirm dialog) and depends on schema decisions R6 hasn't made yet.

Fixed via a new Postgres function, `replace_portfolio_holdings(p_product_id, p_rows)` (migration `replace_portfolio_holdings_rpc`, applied directly to the live Supabase project via the Supabase MCP with the user's explicit go-ahead -- the first rebuild change to touch the live schema rather than just application code). The function does the delete and insert inside one PL/pgSQL transaction, `security invoker` so it stays governed by `portfolio_holdings`' existing RLS (any authenticated user, full read/write -- no privilege escalation introduced), `set search_path = ''` with fully-qualified table references per Supabase's function-hardening guidance. Verified directly against the live database before wiring up the client: inserted 2 test rows, replaced with 1, then attempted a replace with an out-of-range `weight_pct` (violates the table's `0-100` check constraint) and confirmed the prior row survived untouched -- the exact failure mode this was meant to close. Test rows cleaned up afterward; `get_advisors` (security) shows no new warnings, only the pre-existing "RLS policy always true" warnings that reflect the app's already-documented, deliberate no-maker-checker model (`STRATEGY.md` §3). `data/holdings.ts`'s `replaceHoldings()` now calls this via `sb.rpc(...)` instead of separate `.delete()`/`.insert()` calls; `updated_by` is now set server-side via `auth.uid()` inside the function rather than passed from the client, which is also a small security improvement (can't be spoofed by a client-supplied value).

**Independent re-verification pass, same day, before handing back for local build.** Given this sandbox has no working `tsc`, and manual review alone has previously missed real compile errors (see R3's Round 2), a fresh-eyes subagent was sent to independently re-check every R4 file against `data/types.ts`, the design-system barrel export, and the frozen app's original logic -- rather than trusting the original author's own review. It found two real, confirmed bugs and one real data-quality gap:

1. **`lib/exportPdf.ts`: `doc.autoTable(...)` and `doc.internal.getNumberOfPages()` do not compile.** The original file's own doc comment claimed `jspdf-autotable` augments the `jsPDF` class with a typed `.autoTable()` method -- checked directly against the actual published `.d.ts` for the pinned `jspdf-autotable@3.8.2` and `jspdf@2.5.2` (fetched and read, not assumed) and that claim was wrong: no such module augmentation exists in either package. `getNumberOfPages()` is a direct method on `jsPDF`, not nested under `.internal`, contrary to the frozen app's untyped `doc.internal.getNumberOfPages()` (repo root `index.html`) which only worked because it's plain JS reaching past what the type declarations expose. Both call sites would have surfaced as real `tsc` errors on your first local build -- exactly the class of bug this independent pass exists to catch before that happens. Fixed: `pdfTable()` now calls the package's typed default-export function `autoTable(doc, options)` instead of `doc.autoTable(options)`; `pdfFooter()` now calls `doc.getNumberOfPages()` directly. The `readFinalY()` unknown-cast for reading `doc.lastAutoTable` back afterward was independently confirmed still necessary and correct -- neither package types that property at all, though the runtime bundle does set it as a plain side effect of calling `autoTable()`, confirmed by reading the package's actual compiled JS.
2. **`features/products/CsvUploadView.tsx`: a malformed weight column silently wrote `weight_pct: 0` into the real `portfolio_holdings` table**, with no per-row indicator -- only the aggregate ~100% sanity check could catch it, and only if the rest of the CSV was otherwise correct enough to make the total visibly off. Harmless under the frozen app (nothing was persisted); a real data-quality risk now that Save writes to a live table. Fixed: a new `hasValidWeight()` check (distinguishing a genuinely unparseable cell from a real, valid "0") flags invalid rows in red in the preview table and disables Save entirely until they're resolved, rather than letting a bad column mapping silently record a false weight.

Two minor cosmetic findings (the Excel constituents sheet renamed from `"Constituents (Uploaded)"` to `"Constituents"`; some optional-chaining on a field the type system already guarantees is present) were reviewed and left as-is -- neither affects correctness. Full independent-review report available in this session's transcript if wanted later.

**Follow-up fix, second day: PDF Unicode-encoding corruption, font/spacing consistency, and a new Disclosures section.** Triggered by a real bug report against the DSOP product's exported PDF ("weird text after 'trigger events'", plus "inconsistent font sizing and line spacing"), and a separate compliance finding that neither export had any disclosures/disclaimer section at all.

1. **Root cause of the garbled/truncated-looking Rebalance Frequency text, confirmed against live data, not guessed**: queried DSOP's `data->>'rebalanceFrequency'` directly in Supabase -- the stored text is complete and un-truncated (184 chars), so this was never a data problem. It contains a Unicode minus sign (U+2212, "stop-loss breach at −20% from entry") -- a different codepoint from the ASCII hyphen (U+002D) and outside WinAnsiEncoding, the only character set jsPDF's built-in `helvetica` font supports. jsPDF doesn't error on unsupported glyphs; it silently corrupts spacing/kerning for the rest of the line, which reads as both "truncated" and "letter-spaced." Fixed with a new `sanitizePdfText()` in `exportPdf.ts`, applied everywhere this file calls `doc.text()`/`splitTextToSize()`/`autoTable()`: an explicit map for the known-bad characters people actually type in financial prose (the minus sign, ₹, → ← ≤ ≥ ≈), an explicit allowlist for the WinAnsi-safe "smart typography" that already rendered fine (curly quotes, em/en dash, bullet, ellipsis), and a `?`-fallback safety net for anything else outside Latin-1 so a future stray character degrades visibly instead of corrupting the page again.
2. **Font size / line spacing was genuinely inconsistent, not just a subjective impression**: `pdfBody` rendered at 9.5pt with leading `size*0.42+2.2`; `pdfKv`'s value text was hardcoded to 9pt with a hardcoded 4.3mm/line leading; `pdfBullets` used 9.5pt with the same hardcoded 4.3mm/line -- three different leading ratios stacked directly against each other section-to-section (e.g. the Key Facts block vs. the Objective paragraph immediately below it). Fixed by extracting a shared `BODY_SIZE` (9.5) constant and `lineHeight()` formula, now used by all three helpers.
3. **Disclosures section added** to `exportProductPdf`, `exportClientSummaryPdf` (`lib/exportPdf.ts`), `exportProductDocx` (`lib/exportWord.ts`), and the read-only `ProductDetail.tsx` view. New optional `disclosures?: string` field on `ProductNoteCommon` (`data/types.ts`, no migration needed -- lives in the existing `data` jsonb column), editable via a new field in `ProductEditor.tsx`. Falls back to `lib/disclosures.ts`'s `DEFAULT_DISCLOSURES_TEXT` when unset -- **explicitly marked `[DRAFT -- pending compliance/legal review]` in its own text**, written for structural coverage (so the section exists at all) rather than as reviewed compliance copy; it deliberately does not assert any real SEBI registration status or number. Per the user's explicit choice when asked how to source this (draft boilerplate now vs. wait for their exact text vs. structural placeholder only), each product should get its own reviewed `disclosures` text before going investor-facing -- the default is only a fallback, not a finished disclosure.

**Also added, same day: webmail options for "Email This Note".** User feedback: opening the local desktop mail client via `mailto:` is inconvenient when that's not the client actually used day-to-day. `lib/email.ts` gained `buildWebmailUrl()`/`emailNoteVia()` supporting Gmail, Outlook web, and Yahoo compose-in-browser deep links (prefilled subject/body, opened in a new tab so the studio tab isn't lost) alongside the original `mailto:` behavior (kept as a `'default'` option, still used via `buildMailtoUrl()`). `ProductDetail.tsx`'s single "✉ Email This Note" button became four buttons (Gmail/Outlook/Yahoo/Desktop App) rather than a dropdown, to avoid guessing at the design-system's `SelectField`/`FieldRow` layout inside a flat button toolbar without visually verifying it first.

**Goal**: re-implement the three-path Create screen (blank/template/existing) and the Manage Templates CRUD screen.

**Disclosed deviation from the frozen app**: the frozen app's `blankProductShape()` is untyped JS and omits every archetype-specific field (`styleSleeves` etc.) entirely -- fine at runtime, but `ProductNoteData` is a discriminated union where every member requires one of those arrays to actually be present (`lib/archetype.ts`'s type guards all check `Array.isArray(...)`). An object with none of them doesn't structurally satisfy the union. "Start Blank" here defaults to a single-sleeve shape with an empty `styleSleeves: []` and null-valued `portfolioConstructionRules` rather than a truly untyped object -- same visible behavior (nothing pre-filled), but it type-checks.

**Independent re-verification pass, same day, before handing back.** Same reasoning as R4's: a fresh-eyes subagent reviewed all 6 new/changed files against `data/types.ts`, `lib/archetype.ts`, and the design-system's actual prop signatures. Found one real compile blocker and one real logic gap:
1. **`CreateProductView.tsx`: `t[0].id` on an array accessed after only a `.length` check.** With `noUncheckedIndexedAccess` (enabled since R0), TS does not narrow `t[0]` to defined based on a preceding `.length` comparison -- `t[0]` stays typed `TemplateRow | undefined`, so `.id` off it is a real `tsc --strict` error. Fixed: destructured to `const first = t[0]` and guarded on `first` directly.

Fixed: added `validateHasArchetypeShape()` (new `InvalidProductJsonError`), run in addition to `validateTemplateData` specifically on the JSON-import path.

No sandbox compiler run (same standing limitation as every phase since R0) -- both fixes above were caught by the independent review, not a real `tsc` pass; that's still owed before this is trusted.

## R9 — Rebuild the Lite Claude.ai/Cowork artifact companion

**Goal**: replace the current, badly stale "Vriksha Product Note Studio (Lite)" artifact with one that matches the current data model and shares real data with the main app, instead of being a disconnected sandbox.

**Current state (found 2026-07-20, user asked directly whether it had been kept in sync — it had not)**: only a backup snapshot exists on disk (`scratchpad_backups/2026-07-16_202522/artifact_source.html`), and checking its actual code shows it predates even the *original single-file app's own* structured-caps rework — it still uses free-text `weightRange` strings (`"35-55%"`), not the `sleeveMinPct`/`sleeveMaxPct` numeric fields every other surface has used for a long time. It runs entirely on browser `localStorage`, no Supabase, no login. Its own in-app "About" screen says outright: *"this Lite version's local storage is scoped to this artifact and does not sync with the standalone file's data. Treat them as two independent working copies."* So the sync gap was a known, accepted limitation at the time it was built, not a regression — but nobody has revisited it since, and a great deal has shipped in the meantime (Phase 1 Compliance Engine, PDF export, Create/Templates redesign, the freeze, and now this entire React rebuild).

**Why this is scheduled after R8, not sooner**: the Lite artifact should target the *settled* data model, not a moving one. R4 (exports) won't change the schema, but R5 (Create flow/Templates) and R6 (Compliance engine) still can. Building the Lite artifact before those land risks building it twice. One build against the final shape, after cutover, is the efficient order — this matches what the user asked for directly.

**Recommended technical approach** (the user asked for a direct recommendation, not a menu, given they don't work with the underlying constraints day to day — decided here, not left open):

1. **Plain HTML/CSS/JS artifact, not a React artifact.** This matches both the original Lite artifact's own architecture and the frozen main app's (hand-written DOM/string rendering, no component framework) — and avoids a real conflict: React artifacts in this environment are constrained to Tailwind's core utility classes for styling (no custom stylesheet), which would fight the custom Vriksha forest-green/gold palette and Lora/JetBrains Mono typography rather than help express it. A plain HTML artifact can embed an arbitrary `<style>` block, so `tokens.css`'s exact values port over unchanged, the same way the frozen app and the rebuild's `design-system/tokens.css` already do.
2. **Talk to real Supabase, not `localStorage`.** This is the actual fix for the current version's core limitation. It's also not optional: Claude.ai/Cowork artifacts disallow `localStorage`/`sessionStorage` outright in this environment (they fail there), so there is no working "offline persistence" option to fall back to regardless — hitting Supabase directly is both the only viable persistence path available and the one that actually closes the sync gap. Supabase's REST layer (PostgREST for data, GoTrue for auth) is reachable with plain `fetch()` calls using the same publishable anon key and RLS policies the frozen app and rebuild already use — no `@supabase/supabase-js` import needed, so no artifact library restriction applies. Real consequence to design around and disclose up front in the artifact's own UI: with no persistent storage, every fresh artifact load requires signing in again — the session token only lives in memory for that load. Not a bug; a property of the environment.
3. **Deliberately narrower scope than the full app, same philosophy as the original Lite version**: core view / edit / publish / version / diff / archive against the real, current, structured numeric cap fields — not the old free-text ones. Skip Word/Excel export, CSV upload, and the R6 Compliance engine; those need heavier libraries or business logic that don't earn their complexity in a "quick view/edit from inside a chat" tool. A JSON download for getting data out (already proven fine in the current version — a `Blob` plus a downloadable link, no external library needed) covers the same need the old version's CSV/JSON export did.
4. **Read the actual shape from the finished rebuild's `data/types.ts` at build time**, not from memory of what it looked like in this conversation — by R9, R4-R6 will likely have extended it further.

**Verification before calling R9 done**: sign in from the Lite artifact and see the same real products the main app shows (proving it's reading the same Supabase project, not a fork); edit a field, publish a version, and confirm that edit is visible from the main rebuilt app afterward (proving true two-way sync, closing the exact gap flagged above); confirm the artifact still renders and functions correctly after a fresh reload with no prior session (the expected must-re-login behavior, not a broken one).
